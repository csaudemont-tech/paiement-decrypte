Terminal config decoder

A payment terminal decides nothing on its own. Its entire behaviour is written in a configuration file – what it accepts, above which amount it goes online, which card it ignores, when it asks for a PIN. This page explains how that file is organised, then decodes field by field the parameters you find in it, both standard EMV tags and nexo FAST fields.

Nothing is sent anywhere: all decoding happens in your browser.

The five layers of a config

Whatever the vendor or the file format, the information is always stacked in the same order: from the most general (the terminal) to the most specific (the rule that applies to a given card, for a given service). Understand that stack and you understand 90% of config files.

The hardware and its environment: country, currency, displayed languages, what the machine can physically do (chip reader, contactless, magstripe, PIN pad), and whether it is attended by an operator or self-service.

Typical fields: terminalCountryCode, terminalTransactionCurrencyCode, terminalCapabilities, additionalTerminalCapabilities, terminalType. All standard EMV tags, decodable below.

Why it mattersA wrong terminalType (attended when the kiosk is actually unattended) changes the cardholder verification rules the kernel applies. The terminal works, but it does not ask for the PIN where it should.

A list of AIDs (Application Identifier): the identifier of the payment application carried by the chip. If an AID is not in the terminal's list, the matching application is simply invisible – the card may be perfectly valid, it will never be selected.

Every AID starts with a RID (5 bytes) identifying the network: A000000004 for Mastercard, A000000003 for Visa, A000000042 for CB. The rest identifies the product.

Why it mattersOn a CB/Visa co-badged card, both AIDs are present on the chip. It is the terminal configuration – the list, the order, the priorities – that determines which of the two networks processes the transaction. And therefore which interchange schedule applies.

This is the busiest layer, and where most of what you see at the till is decided. For each "card application × requested service" combination (payment, refund, cancellation…), it defines:

the floor limit above which an online authorisation is requested (terminalFloorLimit); the three TACs – Default, Denial, Online – which say how to react to the risk flags raised during the transaction; the contactless limits (transaction limit, threshold above which a PIN is required); the random selection parameters that send a percentage of small transactions online; and the cardholder verification rules.

Why it mattersThe three TACs are the number one source of "why does this terminal decline when the card is fine". They are three masks applied to the same risk flags: Denial declines without going online, Online forces the call, Default decides when the call failed. One misplaced bit in Denial, and a perfectly valid card is declined offline.

Address and protocol of the authorisation host, merchant (MID) and terminal (TID) identifiers, merchant category code (MCC), name and address printed on the receipt, accepted currencies, batch upload parameters.

A single terminal can carry several acquirers: each application profile points to the one it concerns. That is what allows one terminal to send CB transactions to one acquirer and private-label cards to another.

Why it mattersThis is the only layer holding real identifying data (MID, TID, store address, host addresses). It is also the one people forget to anonymise before sending a config file to someone for analysis.

A table indexed by RID + key index, holding the modulus, the exponent and a checksum. It is used for offline data authentication of the card (SDA, DDA, CDA): the terminal verifies the chip's certificate chain without calling anyone.

These keys have an end-of-life date set by the networks, and are replaced in batches through the terminal management system.

Why it mattersA missing or expired key does not cause a visible failure: offline authentication fails silently, the matching flag is raised, and what happens next depends entirely on the layer 3 TACs. Depending on the config, that means "everything goes online" or "everything is declined" – two very different symptoms for the same cause.

Decode a field

The fields below are standard parameters, EMV or nexo FAST: their meaning is identical across vendors, whatever the file format. Every decode shows the specification section it comes from. Pick a field, paste the value found in your config.

A nexo tag cannot be read without its block

This is the main trap in these files, and nothing on screen warns you about it: inside a constructed block, DFxx tags are local to that block. The same tag means something entirely different from one table to the next. A decoder that resolves tags flatly gets it wrong, silently.

Three examples straight from the specification:

  • DF03 is Supported Services in the Application Profile Selection Table, CA Public Key Algorithm Indicator in the CA Public Key Table, and Application Label in the default kernel per AID table.
  • DF01 has fourteen different meanings depending on the block: profile AID, terminal RID, acquirer number, limit set ID, DCC prefix…
  • DF10 on its own is Service Settings, but DF10 inside the selection table is Application Profile Kernel ID. Same tag, two definitions, in the same file.

Labels stay in normative English: these are the identifiers you use to find the row in the specification. Source: data dictionary of , entry tables of the 15 constructed blocks.

Sources – EMV 4.3 Book 3 (Application Specification) and Book 4 (Other Interfaces), EMVCo Contactless Book A/B, ISO 3166-1 and ISO 4217 lists. nexo fields are decoded from the data dictionary of the nexo FAST Part 1 v3.3 specification (sections 13.1 to 13.4), whose notice grants use for the purpose of implementing the specification. Every decode cites the section it comes from.
