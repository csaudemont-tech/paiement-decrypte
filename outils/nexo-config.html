Deux champs sourcés et démontrables ci-dessous (valeurs d'exemple, aucune donnée réelle). Objectif : valider le format de "field card" avant de l'étendre au reste du vocabulaire nexo/OSCAR. Les deux champs non sourcés sont listés en bas, avec ce qu'il manque pour avancer.

terminalCapabilities — réutilise la table déjà validée du décodeur EMV existant (tag 9F33). Source : EMV 4.3 Book 4, Annexe A2 (Terminal Capabilities) — table partagée avec emv-parser via emv-dictionary.js, pas une copie locale.
additionalTerminalCapabilities — sourcé pour ce prototype (tag 9F40), et depuis rapatrié dans emv-dictionary.js pour qu'emv-parser en profite aussi. Source : EMV 4.3 Book 4, Annexe A3, Tables 28-32, p.118-120 (5 octets : type de transaction ×2, saisie, sortie ×2).

Capacités du terminal tag EMV 9F33

<terminalCapabilities>

Ce que le terminal sait faire côté lecture de carte et vérification porteur : saisie manuelle, piste magnétique, puce contact ; méthodes de vérification (PIN, signature, aucune) ; méthodes d'authentification offline (SDA/DDA/CDA). 3 octets, 12 des 24 bits définis par la norme (le reste RFU).

exemple, pas une valeur réelle
OctetBitSignification

Capacités additionnelles du terminal tag EMV 9F40

<additionalTerminalCapabilities>

Complète 9F33 : types de transaction acceptés (achat, cash, cashback, retrait...), capacités de saisie (clavier numérique, touches fonction...) et de restitution (impression, affichage, table de code ISO 8859). 5 octets.

exemple, pas une valeur réelle
OctetBitSignification

Champs identifiés, pas encore sourcés

Ces deux champs apparaissent dans tes fichiers (valeurs observées à titre indicatif, ex. configuredServices=F200/F600, defaultCardService=01) mais je n'ai trouvé aucune définition bit à bit dans les sources autorisées (nexo FAST v3.1 Part 1, EMV Book 3/4, C-2-Kernel-2, PCI officiel) — ce ne sont a priori pas des tags EMV standard ni des éléments nexo-FAST documentés publiquement, plutôt des paramètres propres au schéma du logiciel qui a généré ces fichiers (namespace schemas.artifact.pl/oscarv4).

  • configuredServices — bitmask 2 octets. Hypothèse à vérifier : liste des services de transaction actifs (vente, remboursement, annulation, pré-autorisation...), mais sans confirmation.
  • defaultCardService — 1 octet, ressemble à une valeur d'énumération plutôt qu'un bitmask (service par défaut sélectionné parmi la liste ci-dessus).

Pour avancer sans deviner : si tu as une doc du fournisseur du schéma OSCAR (même un extrait générique, pas spécifique à un déploiement), ou si tu peux confirmer/infirmer l'hypothèse depuis ton expérience terrain, je bâtis la table dessus. Sinon ces deux champs restent hors dictionnaire v1, plutôt que d'inventer une explication non vérifiée.
