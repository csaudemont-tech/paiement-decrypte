Diff de config terminal – comparer deux fichiers XML nexo

Colle ou charge deux fichiers de configuration terminal en XML (blocs e0 à f2) : le comparateur apparie les enregistrements par leur clé métier (AID, RID, TAID, BIN…), distingue un simple déplacement d'un vrai ajout/suppression, et décode les champs bit à bit (capacités du terminal, TAC, paramètres nexo). Les blocs identiques restent repliés.

Tout se passe dans le navigateur. Les fichiers collés/chargés ne sont jamais envoyés à un serveur - le parsing et le diff tournent en JS côté client uniquement. Utile puisque ces fichiers contiennent souvent des identifiants commerçant/acquéreur réels.

Un tag nexo ne se lit pas sans son bloc

C'est le piège principal de ces fichiers, et il ne se voit pas à l'œil nu : à l'intérieur d'un bloc construit, les tags DFxx sont locaux au bloc. Le même tag change complètement de sens d'une table à l'autre. Un décodeur qui résout les tags à plat se trompe sans rien signaler.

Trois exemples tirés de la spécification :

  • DF03 vaut Supported Services dans la table de sélection des profils applicatifs, mais CA Public Key Algorithm Indicator dans la table des clés publiques, et Application Label dans la table des kernels par AID.
  • DF01 a quatorze sens différents selon le bloc : AID du profil, RID du terminal, numéro d'acquéreur, identifiant de jeu de plafonds, préfixe DCC…
  • DF10 seul désigne Service Settings, mais DF10 dans la table de sélection désigne Application Profile Kernel ID. Le même tag, deux définitions, dans le même fichier.

Source : dictionnaire de données de , tables d'entrée des blocs construits. Les intitulés restent en anglais normatif : ce sont les identifiants avec lesquels on retrouve la ligne dans la spécification.
