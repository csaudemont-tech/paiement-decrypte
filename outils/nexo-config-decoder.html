Décodeur de config terminal

Un terminal de paiement ne décide de rien tout seul. Tout son comportement est écrit dans un fichier de configuration – ce qu'il accepte, à partir de quel montant il appelle, quelle carte il ignore, quand il demande un code. Cette page explique comment ce fichier est organisé, puis décode champ par champ les paramètres qu'on y trouve, aussi bien les tags EMV standard que les champs nexo FAST.

Aucune donnée n'est envoyée : tout le décodage se fait dans votre navigateur.

Les cinq étages d'une config

Peu importe le fournisseur ou le format du fichier, l'information est toujours empilée dans le même ordre : du plus général (le terminal) au plus spécifique (la règle qui s'applique à une carte donnée, pour un service donné). Comprendre cet empilement, c'est comprendre 90 % des fichiers de config.

Le matériel et son environnement : pays, devise, langues affichées, ce que la machine sait faire physiquement (lecteur puce, sans contact, piste, clavier PIN), et si elle est surveillée par un opérateur ou en libre-service.

Les champs typiques : terminalCountryCode, terminalTransactionCurrencyCode, terminalCapabilities, additionalTerminalCapabilities, terminalType. Tous sont des tags EMV standard, décodables ci-dessous.

Pourquoi ça compteUn terminalType mal renseigné (attended alors que la borne est en libre-service) change les règles de vérification du porteur appliquées par le noyau. Le terminal fonctionne, mais il ne demande pas le code là où il devrait.

Une liste d'AID (Application Identifier) : l'identifiant de l'application de paiement portée par la puce. Si un AID n'est pas dans la liste du terminal, l'application correspondante est purement invisible – la carte peut être parfaitement valide, elle ne sera jamais sélectionnée.

Chaque AID commence par un RID (5 octets) qui identifie le réseau : A000000004 pour Mastercard, A000000003 pour Visa, A000000042 pour CB. Le reste identifie le produit.

Pourquoi ça compteSur une carte co-badgée CB/Visa, les deux AID sont présents sur la puce. C'est la configuration du terminal – la liste, l'ordre, les priorités – qui détermine lequel des deux réseaux traite la transaction. Donc quel barème d'interchange s'applique.

C'est l'étage le plus chargé, et celui où se joue l'essentiel de ce qu'on observe en caisse. Pour chaque combinaison « application de la carte × service demandé » (paiement, remboursement, annulation…), il définit :

le seuil plancher au-delà duquel on demande une autorisation en ligne (terminalFloorLimit) ; les trois TAC – Default, Denial, Online – qui disent comment réagir aux drapeaux de risque levés pendant la transaction ; les plafonds sans contact (limite de transaction, seuil au-delà duquel on demande un code) ; les paramètres de sélection aléatoire qui envoient en ligne un pourcentage de petites transactions ; et les règles de vérification du porteur.

Pourquoi ça compteLes trois TAC sont la source n°1 des « pourquoi ce terminal refuse alors que la carte est bonne ». Ce sont trois masques appliqués aux mêmes drapeaux de risque : Denial refuse sans appeler, Online force l'appel, Default tranche quand l'appel a échoué. Un bit mal placé dans Denial, et une carte parfaitement valide est refusée hors ligne.

Adresse et protocole de l'hôte d'autorisation, identifiants du commerçant (MID) et du terminal (TID), code d'activité du commerçant (MCC), nom et adresse imprimés sur le ticket, devises acceptées, paramètres de télécollecte.

Un même terminal peut porter plusieurs acquéreurs : chaque profil applicatif pointe vers celui qui le concerne. C'est ce qui permet, sur un même TPE, d'envoyer les CB à un acquéreur et les cartes privatives à un autre.

Pourquoi ça compteC'est le seul étage qui contient des données identifiantes réelles (MID, TID, adresse du magasin, adresses des hôtes). C'est aussi celui qu'on oublie d'anonymiser avant d'envoyer un fichier de config à quelqu'un pour analyse.

Une table indexée par RID + index de clé, contenant le module, l'exposant et une empreinte de contrôle. Elle sert à l'authentification hors ligne des données de la carte (SDA, DDA, CDA) : le terminal vérifie la chaîne de certificats de la puce sans jamais appeler personne.

Ces clés ont une date de fin de vie fixée par les réseaux, et sont remplacées par lots via le système de télégestion.

Pourquoi ça compteUne clé absente ou périmée ne provoque pas une panne visible : l'authentification hors ligne échoue silencieusement, le drapeau correspondant est levé, et la suite dépend entièrement des TAC de l'étage 3. Selon la config, ça donne « tout passe en ligne » ou « tout est refusé » – deux symptômes très différents pour la même cause.

Décoder un champ

Les champs ci-dessous sont des paramètres standard, EMV ou nexo FAST : leur signification est identique chez tous les fournisseurs, quel que soit le format du fichier. Chaque décodage affiche la section de la spécification dont il vient. Choisissez un champ, collez la valeur trouvée dans votre config.

Un tag nexo ne se lit pas sans son bloc

C'est le piège principal de ces fichiers, et rien à l'écran ne vous en avertit : à l'intérieur d'un bloc construit, les tags DFxx sont locaux au bloc. Le même tag change complètement de sens d'une table à l'autre. Un décodeur qui résout les tags à plat se trompe sans rien signaler.

Trois exemples tirés de la spécification :

  • DF03 vaut Supported Services dans la table de sélection des profils applicatifs, mais CA Public Key Algorithm Indicator dans la table des clés publiques, et Application Label dans la table des kernels par AID.
  • DF01 a quatorze sens différents selon le bloc : AID du profil, RID du terminal, numéro d'acquéreur, identifiant de jeu de plafonds, préfixe DCC…
  • DF10 seul désigne Service Settings, mais DF10 dans la table de sélection désigne Application Profile Kernel ID. Le même tag, deux définitions, dans le même fichier.

Les intitulés restent en anglais normatif : ce sont les identifiants avec lesquels on retrouve la ligne dans la spécification. Source : dictionnaire de données de , tables d'entrée des 15 blocs construits.

Sources – EMV 4.3 Book 3 (Application Specification) et Book 4 (Other Interfaces), EMVCo Contactless Book A/B, listes ISO 3166-1 et ISO 4217. Les champs nexo sont décodés d'après le dictionnaire de données de la spécification nexo FAST Part 1 v3.3 (sections 13.1 à 13.4), dont la notice autorise l'usage aux fins d'implémentation. Chaque décodage cite la section dont il vient.
